It is a durable continuation point for:
- architecture documentation work

This handoff does not claim that the codebase is already aligned to these decisions.
It records the approved target architecture.

## Executive summary

KmiDi is a hybrid AI-assisted music creation system for beginners and experts.
The product is plugin-first in launch priority, but the internal architecture must preserve a future path to a standalone native engine.

Canonical truths:
- musical intent: validated Intent IR
- live generated audio/music state: native engine runtime
- host-facing persistence/restore state: plugin/runtime state contract
- user project/session state: plugin/runtime project layer
- generation result metadata: Python backend

Hard priorities:
1. real-time safety
2. correctness
3. plugin stability
4. iteration speed
5. UX fluidity
6. model experimentation

Core usability must survive AI/backend failure:
- plugin loading
- playback
- core editing
- saved project loading
- non-AI authoring workflows

## Approved pass outcomes

### Pass A — Global architecture principles

- Product center: DAW/plugin runtime
- Architecture center of gravity: plugin runtime first, with explicit future extraction path to standalone native engine
- Intent IR is canonical for engine-facing and persisted intent
- Native engine owns live runtime truth
- Plugin/runtime project layer owns project/session truth
- User control/customization must not be sacrificed for speed
- Partial coexistence during migration is acceptable
- Ownership patterns are intentionally rigid
- Generation orchestration and model/backend experimentation remain flexible
- Intent semantic changes are permanently human-owned

Agent safety boundaries:
- Freer refactor surfaces: non-ABI C++ implementation files, Python orchestration internals
- Strict-checklist-only surfaces: JUCE ownership surfaces, FFI bridge code, project state serialization
- Always human-reviewed: exported ABI changes, Intent semantic changes, persistence model changes
- Maximum agent blast radius: one module

Offline/local-only requirements:
- core editing
- plugin runtime
- playback
- saved project loading
- non-AI authoring workflows

Graceful degradation requirements:
- plugin loading
- manual editing
- transport/runtime control
- model provider outage
- backend offline
- DAW transport quirks
- missing audio/MIDI devices
- cloud auth failure

### Pass C — Intent IR / data contract architecture

- Intent IR is the single canonical language for engine-facing and persisted intent
- Native engine, plugin/runtime, Python backend, and persistence layer must speak Intent IR natively
- UI drafts, orchestration forms, API DTOs, and importers may translate into Intent IR from looser local models
- The following must never bypass Intent IR:
  - plugin -> engine
  - persisted project intent
  - backend -> engine generation requests
- Semantic authority order:
  1. shared_schemas
  2. Rust validator
  3. product docs
  4. Python request schema
- Rust validator is the canonical validator of last resort
- Breaking schema changes are allowed only at explicit version boundaries
- Persisted projects must remain loadable forever through migration
- API compatibility may be transitional; persisted project compatibility is stronger
- Defaults belong in normalization/migration, not engine runtime
- Intent becomes immutable after validation for persisted/engine-facing usage
- Codegen is the preferred sync mechanism across TS/Rust/Python
- Generated TS intent types, Rust generated intent types, and Python validation mirrors must never be hand-edited
- Drift checks must fail on:
  - schema sync drift
  - Rust validator/tests
  - Python schema tests
  - generated diff mismatches
- Agents may edit schema plus generated artifacts in one task only with strict checks; semantics changes still require human review

Canonical flow:
UI draft -> normalize -> validate Intent IR -> orchestrate -> engine adapt -> playback/render

### Pass D — Native engine architecture

Engine role:
- own and execute low-latency musical runtime behavior safely and deterministically
- own live audio state
- perform timing-sensitive transformation
- apply validated Intent IR to runtime behavior

Native is primarily:
- DSP/audio runtime
- low-latency generation/control

Permanently excluded from native:
- cloud/network concerns
- UI/view concerns
- product/session persistence authority
- model-provider-specific orchestration
- semantic authority over intent definitions
- long-latency backend workflow control

Long-lived native objects:
- EngineRuntime / EngineSession
- Transport/Timeline state
- AudioGraph or DSPCore
- Parameter/Control state store
- Intent adaptation/application state
- Resource managers
- RT-safe queue/snapshot bridge objects

Ownership/lifetime rules:
- plugin/runtime layer owns EngineRuntime lifetime
- EngineRuntime uniquely owns core runtime subsystems
- RT path borrows stable non-owning references only
- UI/backend never directly own runtime-critical native objects
- single-owner only for runtime root, DSP root, transport/timeline owners, resource managers, worker threads, and lifetime-critical queues/buffers
- shared ownership allowed only for immutable shared assets, expensive shared non-RT resources, and read-mostly non-RT-critical blobs
- raw pointers are acceptable only as non-owning observers

Shutdown/mutation rules:
- plugin/runtime control layer creates engine/session state
- owning plugin/runtime layer tears it down through one ordered shutdown path
- engine runtime may outlive editor/UI state
- observers/callbacks/ingress die first during shutdown
- runtime mutation is only through native control surfaces
- non-RT -> RT mutation uses commands/snapshots/queues
- atomics are narrow scalar tools only
- locks are forbidden on RT-critical paths
- audio-thread mutable state must be explicitly predeclared, bounded, allocation-free, and lock-free

Error/modernization rules:
- recoverable errors use explicit status/result forms
- fatal contract violations fail fast in dev/test and degrade in controlled ways in release where possible
- no exceptions across FFI
- no exceptions on RT paths
- modernization strategy is wrapper-first at dangerous boundaries, then aggressive RAII modernization inside contained subsystems with explicit ownership roots
- too risky for agent-led structural rewrites without human approval:
  - plugin lifecycle roots
  - processBlock/RT callback architecture
  - exported ABI ownership surfaces
  - persistence/serialization roots
  - cross-language lifetime contracts
  - transport/timeline mutation core

### Pass E — JUCE / plugin / real-time rules

Canonical architecture:
- host-facing plugin shell owns lifecycle, persistence, and host integration
- separable native engine owns live runtime execution
- plugin is first-class product shell, not owner of musical truth

Responsibility split:
- PluginProcessor owns lifecycle integration, parameter/automation bridge, serialization boundary, EngineRuntime ownership, RT callback entrypoint, transport/host adapter, and minimal host->engine control plumbing
- PluginEditor owns UI/presentation, transient UI state, visualization, command issuance, and safe observation/subscription only
- Engine/DSP core owns live execution, DSP/audio graph behavior, timing-sensitive control application, validated runtime config application, RT-safe transitions, and audio-result production
- Background workers own non-RT preprocessing, expensive analysis/precompute, backend/model interaction outside RT, resource preparation, and command/snapshot preparation

Thread model:
- relevant threads: audio, message/UI, background workers, model/backend orchestration, I/O/resource loading, timer/async ingress surfaces
- audio thread allows RT-safe processing only
- forbidden on audio thread:
  - allocation
  - locks/blocking waits
  - file/network I/O
  - model/backend calls
  - unbounded logging
  - uncertified FFI/Python calls
  - exceptions
  - unsafe dynamic graph mutation
- no locks on audio thread
- no allocations on audio thread
- no syscalls/network/model inference on audio thread

Communication model:
- non-RT -> RT: explicit command/snapshot handoff through bounded preallocated RT-safe queues/buffers using only prevalidated stable data
- RT -> UI: one-way snapshot publication or bounded telemetry/event queue
- sanctioned primitives:
  - snapshots/double buffers for compound state
  - bounded lock-free queue/ring buffer for commands/events
  - atomics only for narrow scalar state
- RT sees coherent fully formed updates only
- UI may see slightly stale snapshots
- no torn compound state is allowed

JUCE ownership/lifecycle rules:
- Component ownership: direct member ownership where practical, otherwise std::unique_ptr
- owning raw Component* is forbidden
- child widgets are owned by parent via direct members or std::unique_ptr
- OwnedArray/ScopedPointer tolerated only in quarantined legacy compatibility zones; forbidden in new architectural code
- new default ownership: std::unique_ptr unless direct member ownership is better or JUCE requires otherwise
- SafePointer mandatory for deferred/timer/async callbacks into Components/Editors and worker completion callbacks into UI
- async work must be explicitly canceled/disconnected/invalidated before target destruction

Lifecycle hazards to defend against:
- post-close editor callbacks
- stale UI references into processor/runtime
- worker completion into dead UI
- processor teardown with active ingress
- runtime teardown with outstanding RT/mutation references
- persistence/shutdown collisions

Required preconditions:
- before editor close: detach listeners/subscriptions, stop timers/updaters/deferred callbacks, cancel/guard worker callbacks, sever post-close observation paths, keep runtime continuity intact
- before processor shutdown: stop new ingress, detach editor-facing observers, stop/cancel background activity, quiesce runtime mutation pathways, remove RT dependence on dying resources, then perform ordered teardown
- before project/session unload: flush/reject pending commands to old state, persist through defined boundary if needed, detach UI/project observers, transition runtime via validated coherent session swap, forbid lingering old-session references

Performance/determinism:
- most important budgets:
  - audio callback deadline safety
  - bounded non-RT -> RT control latency
  - stable plugin load/open/close behavior
  - responsive UI without harming RT
  - predictable load/restore timing
- unacceptable jitter:
  - audio overruns/glitches
  - unstable timing of runtime control application
  - host automation/transport response instability
  - backend/model delays leaking into runtime behavior
- deterministic behavior required for engine-facing runtime interpretation and persisted project replay except where stochastic behavior is explicitly marked
- acceptable latency variance:
  - RT/runtime tight
  - UI mild
  - backend/model broader only if isolated from core runtime and control continuity

### Pass F — FFI / ABI / cross-language ownership

KellyFFI role:
- narrow explicit memory-safe-by-contract control/data boundary into native runtime and Intent IR
- not a broad convenience mirror of internal objects

ABI policy:
- narrow stable ABI
- expansion only through deliberate reviewed versioned additions
- breaks allowed only with explicit version boundary and human review
- break process requires:
  - version bump
  - header/contract update
  - consumer-impact review
  - binding/test updates
  - compatibility or migration notes
  - CI/build/test gates
- manual compatibility policy first; heavier symbol versioning only if later justified

Consumers:
- Python bindings/backend
- tests/benchmarks
- internal tooling
- possible future external apps only if ABI discipline is maintained

Allowed FFI styles:
- opaque handles with create/destroy pairs
- caller-provided output buffers where practical
- immutable returned snapshots/structs with explicit free if callee allocates
- borrowed pointers only when lifetime is trivial and documented
- static immutable data only when clearly non-freeable

Ownership rules:
- dominant exported styles should be opaque handles, caller-owned output buffers, immutable callee-allocated snapshots with exact free pair, and tightly bounded borrowed read access
- allocating side frees
- only matching ABI free/destroy may release allocated memory
- free on non-RT threads by default
- no runtime/structural handle may outlive its owning session/runtime
- detached immutable copied snapshots may outlive if explicitly documented
- handles cross threads only when explicitly documented thread-safe

Rust/C++ rules:
- each side owns what it allocates
- Rust FFI allocations are freed by Rust free functions
- C++ may copy/internalize Rust outputs into native-owned forms
- C++ may not retain undocumented long-lived references into Rust-owned allocations
- Rust panics must never cross the FFI boundary
- Rust validation failure returns structured nonfatal errors, must not partially initialize runtime state, and must not silently coerce invalid intent into engine truth

Python rules:
- no general exposure of raw ownership-sensitive pointers to Python
- Python uses opaque handles, copied data, serialized payloads, or managed bindings
- stable C ABI remains primary even if binding technology evolves
- lifetime safety must be enforced both in the C ABI and in the binding layer

Banned FFI patterns:
- undocumented ownership transfer
- raw internal object pointers as public API
- guessed/free-form deallocation rules
- cross-allocator frees
- unsynchronized mutable shared cross-language structures
- exceptions/panics crossing FFI
- undocumented thread-affinity requirements

Agent rule:
- adding exported symbols requires explicit human approval

## Cross-pass non-negotiable rules

1. Plugin-first product, engine-separable internals
- host-facing plugin shell ships first
- host-facing code must not become the permanent owner of musical truth or runtime truth

2. Intent IR is canonical where correctness matters
- engine-facing and persisted intent must converge into validated Intent IR
- looser UI forms are allowed only before normalization/validation

3. Native engine owns live runtime truth
- plugin/runtime owns project/session/persistence truth
- Python backend owns generation metadata, not live runtime truth

4. Core usability must survive AI/backend failure
- plugin load, playback, core editing, saved project loading, non-AI authoring must remain usable offline/local-first

5. Persisted project compatibility is a long-term promise
- old saved projects remain loadable via migration

6. Ownership discipline dominates
- unique ownership by default
- shared ownership only in narrow non-RT cases
- raw pointers are observer-only

7. RT discipline is absolute
- no locks
- no allocation
- no network/syscalls/model calls
- no uncaught exceptions
- no unsafe dynamic mutation

8. FFI is a deliberate bridge, not a shortcut
- narrow ABI
- explicit allocator ownership
- no ambiguous lifetime rules
- no new exported symbols without human approval
